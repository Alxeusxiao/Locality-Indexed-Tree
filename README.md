# LI-Tree —— 截断式近似 CDF 字符串索引

> **命名**：`LI` = **L**ocality-**I**ndexed，"按前缀局部性建索引"。有序数据里相同前缀的键天然聚成连续一段，LI-Tree 把「前缀 → 数组区间」这件事预先算成一张 CDF 表，查询时直接查表而不必比较。GitHub 仓库名建议用 `li-tree`。

在一份**已按字典序排好序**的字符串数组上，把 `log₂(N)` 的二分查找压缩成「**O(1) 查表定位 + 少量桶内比较**」。

以 100 万条、平均 78 字符的随机字符串为例：二分平均需要 **18.96** 次字符串比较，LI-Tree 只需要 **6.15** 次，墙钟时间约为二分的 **0.7×**。

这是对一个 2022 年课程/实验项目的重构版本：算法思路保留，修掉了若干会算错或崩溃的缺陷，补齐构建脚本、实验方法与文档。全部结论都可用 `make run-bench` 在本机复现。

## 效果速览

数据：`li-gen --count 1000000 --dist nd --seed 1`，10 万次查询/组，`-O2`。

| 算法 | 命中·平均比较 | 命中·平均耗时 | 相对二分 | 未命中·平均比较 |
|---|---|---|---|---|
| 二分查找 | 18.9556 | 0.526 µs | 1.00× | 19.9513 |
| 插值查找 | 5.1836 | 1.355 µs | 2.58× | 5.5972 |
| 简易插值 | 68879.2 | 382.7 µs | 728× | 69005.8 |
| 割线查找 | 4.9532 | 1.202 µs | 2.29× | 5.1499 |
| **LI-Tree** | **6.1463** | **0.351 µs** | **0.67×** | **6.6798** |

> 注意一个反直觉的现象：插值法和割线法的**比较次数比二分少得多**，但**墙钟时间反而更慢**。原因是每一步都要把字符编码成 94 进制整数（几十条整数指令 + 一次除法 + 一次访存），而一次 `strcmp` 通常在前几个字节就分出大小、并且很可能命中缓存。**比较次数不是这个负载上的瓶颈**，详见 [docs/项目说明.md §8.5](docs/项目说明.md)。

## 多核加速

查询循环与建索引的直方图都支持并行（`--threads N`，`--threads 0` 表示用满全部核，默认 1）：

| 线程 | 查询耗时·LI-Tree 命中 | 加速比 | 建索引·100 万条 | 加速比 | 建索引·500 万条 | 加速比 |
|---|---|---|---|---|---|---|
| 1 | 0.372 µs | 1.00× | 7.85 ms | 1.00× | 41.3 ms | 1.00× |
| 2 | 0.165 µs | 2.25× | 5.25 ms | 1.49× | — | — |
| 4 | 0.082 µs | 4.54× | 4.37 ms | 1.80× | 22.4 ms | 1.84× |
| 8 | 0.051 µs | 7.29× | 3.72 ms | 2.11× | 17.0 ms | 2.43× |
| 16 | 0.038 µs | 9.83× | 3.27 ms | 2.40× | 15.4 ms | 2.69× |

三条性质：

- **`--threads 1`（默认）与单线程版本逐位一致**（task 0 沿用全局随机流），所以文档里所有单线程数字仍然成立；多线程时各线程用独立随机流，平均比较次数波动约 ±0.2%。
- **并行不改变索引内容**：1 线程和 16 线程构建出的索引，`li-demo` 的查找结果逐行完全相同。
- **建索引只加速到约 2.7×**，不是 16×——它已经撞上内存带宽上限（直方图要扫过全部行，500 万条 ≈ 320 MB 有效流量）。查询循环因为计算占比更高，能到 9.8×。
- **不是线程越多越好**：线程创建开销固定，查询量太小时会盖过收益（32 线程跑 2 万次查询反而不如 16 线程）。经验值是查询数不少于 `线程数 × 1000`。

本机 32 个逻辑核，`make run-bench-mt` 一键复现上表。

## 核心思路

```
                  ┌────────────────────────────────┐
   查询 key ─────▶│ ① 公共前缀比对 O(start_bit)     │── 不一致 ─▶ 不存在
                  └───────────────┬────────────────┘
                                  ▼
                  ┌────────────────────────────────┐
                  │ ② 截断前缀 → 94 进制整数 v      │
                  └───────────────┬────────────────┘
                                  ▼
                  ┌────────────────────────────────┐
                  │ ③ 桶号 k = (v − num0) / division│  ← 零次字符串比较
                  │    候选区间 = [cdf[k], cdf[k+1])│
                  └───────────────┬────────────────┘
                                  ▼
                  ┌────────────────────────────────┐
                  │ ④ 该桶有子节点? ─ 是 ─▶ 递归     │
                  │                └─ 否 ─▶ 桶内二分│
                  └────────────────────────────────┘
```

关键在于第 ③ 步：原版是靠"猜位置"（插值/割线）逼近，LI-Tree 是直接**查一张前缀和表**，把"猜"变成"查"。最后一层只在平均 `cap` 个元素上二分，所以总比较次数从 `log₂(N)` 降到 `常数 + log₂(cap)`。

两种构建方案（`--scheme`）：

| | 方案一 `--scheme 1`（默认） | 方案二 `--scheme 2` |
|---|---|---|
| 截断位数 | 按"每单位值的元素数 ≤ cap"自动加长 | 固定 2 字符 |
| `division` | `cap / 平均每单位值的元素数`（≥1） | 固定 1 |
| CDF 长度 | ≈ `N / cap`，随数据自适应 | 等于值域跨度，最多 94² = 8836 |
| 可扩展性 | **桶内元素数对 N 不敏感** | 桶内元素数 = `N / 8836`，随 N 变差 |

500 万条时两者拉开差距：方案一自动把截断加长到 3 字符（39552 桶，6.31 次比较），方案二仍是 8836 桶（8.42 次比较）。见 [docs/项目说明.md §8.3](docs/项目说明.md)。

## 快速开始

```bash
make               # 构建到 build/
make run-small     # 10 万条数据 + 演示 + 基准，一遍跑通自检
make run-bench     # 复现上表的完整实验（100 万条）
make run-bench-mt  # 多核扩展性测试（1/2/4/8/16 线程）
make help          # 列出全部目标
```

手动分步：

```bash
build/li-gen   --out build/data/keys_1m.txt --count 1000000 --dist nd --seed 1 --check
build/li-demo  --data build/data/keys_1m.txt --keys 1000000 --scheme 1
build/li-bench --data build/data/keys_1m.txt --keys 1000000 --queries 100000 --scheme 1 --cap 150
```

环境要求：**gcc + GNU make**（Windows 用 MinGW-w64 的 `mingw32-make`）。代码是 C11，支持 Windows / Linux / macOS；Windows 下用 `QueryPerformanceCounter` 计时，其他平台用 `clock_gettime`。

## 命令参考

### `li-gen` 生成数据集

```
li-gen --out <文件> [--count N] [--dist uniform|nd|nd2|normal|mix] [--seed S] [--check]
```

5 种分布：均匀、首位尖峰、双尖峰、正态、混合高斯。`--check` 校验有序性与字符范围（字符必须全部落在 `'!'`~`'~'`，这是 94 进制编码的前提）。同种子必得同一份数据。

### `li-demo` 单次演示

```
li-demo --data <文件> [--keys N] [--scheme 1|2] [--cap C] [--threads T] [--seed S]
```

打印 **随机命中 / 随机未命中 / 最大键** 三类查询在五种算法下的位置与比较次数，每个结果都带 `[正确]` / `[异常]` 标记。最大键那条是专门的边界回归用例。`--threads` 只影响建索引。

### `li-bench` 主实验

```
li-bench --data <文件> [--keys N] [--queries Q] [--scheme 1|2] [--cap C] [--repeat R] [--threads T] [--seed S]
```

统计数据：建索引耗时、索引规模、命中/未命中两组的平均比较次数与平均耗时。**每个结果都校验"返回位置上的字符串是否等于 key"，并统计错答次数**；有错答时退出码为 1，可直接接 CI。`--threads` 同时并行查询循环与建索引直方图。

## 与原版的关系

原始实现是四个互相复制粘贴的单文件（`test_single.c` / `test_numbers.c` / `*_m2.c`），本仓库把它重构成模块化工程并修掉了 9 处缺陷。**这些原始文件与当年的数据集已在仓库清理时移除**，其缺陷与实测证据整理在详版文档里。其中最严重的一处是：

> 原版统计直方图时写 `for (i = start; i < end; ++i)`，而区间语义是**闭区间** `[start, end]`。结果是**每个节点负责区间最右端的那个键永远进不了索引**。实测查最大键时二分命中、索引返回"未命中"；因为只有边界键受影响（概率约 `节点数/N`），加上原版返回的是"比较次数"而不是位置，这个 bug 一直没被发现。

完整清单与证据见 [docs/项目说明.md §9](docs/项目说明.md)。

重构后与原版程序在同一份数据上的对照（比较次数，偏差 < 0.1%；原版程序与那批数据已在清理时移除，本表仅作保真度证据）：

| 算法 | 原版 | 重构版 |
|---|---|---|
| 二分（100 万） | 18.952090 | 18.9556 |
| ACDF（100 万） | 6.385564 | 6.3908 |
| 二分（500 万） | 21.320825 | 21.3215 |
| ACDF（500 万，方案二） | 8.196986 | 8.2010 |
