## 1. 项目简介

本工程研究一个很窄但很实际的问题：**在一份静态、已排序的长字符串集合上做等值查找，怎样才能比二分更快。**

传统答案是"插值查找 / 割线查找"这类**数值近似**方法：把字符串前几个字符按某个进制编码成整数，用这个整数估算目标在数组中的大致位置，再在附近细找。它们的优点是每一步都能把范围缩得很小，缺点是对数据分布极度敏感——分布一偏，估算就会失准，退化得比二分还差（实测简易插值在 100 万条上要做 6.9 万次比较）。

本项目实现的 **LI-Tree** 换了个思路：既然数据已经排好序，那"每个字符前缀对应数组的哪一段"是可以**预先算好并查表**的。把估算换成查表，就把"猜不准"这个不确定性彻底消掉了。

工程上它对应一个**截断树**：

- 每个节点负责一段连续区间，先剥掉区间内所有键都相同的**公共前缀**；
- 再取接下来若干字符，按 94 进制编码成整数，把值域切成若干桶；
- 用一张**前缀和表（CDF）**记录"每个桶之前的元素个数"，于是查询时一次除法就能算出自已该去哪个桶、桶里的候选区间是哪一段；
- 桶内元素仍然太密时递归建子节点，下一层用更长的前缀继续区分。

最终效果：100 万条数据上，平均比较次数从二分的 **18.96** 降到 **6.15**，墙钟时间降到 **0.7×**；500 万条上比较次数基本不变（**6.31**）。

## 2. 问题定义

**输入**：`N` 条字符串，每条长度 31~126 字符，字符取自 94 个可打印 ASCII（`'!'`…`'~'`），整个数组已按 `strcmp` 升序排列。

**查询**：给定 key，返回它在数组中的下标；不存在返回 −1。

**约束**：

- 索引是**静态**的，构建后不再插入/删除（数据一次性生成，只读）；
- 字符串长度固定槽宽 128 字节（便于 `strcmp` 直接比较，也便于按数组下标跳转）；
- 只统计 **`strcmp` 调用次数**作为算法代价的主要指标，同时测量整段查询的墙钟时间。

## 3. 算法原理

### 3.1 三个观察

1. **前缀是冗余的。** 有序数组里，相邻元素往往共享一长串前缀。对区间 `[start, end]` 而言，`row[start]` 与 `row[end]` 的公共前缀长度 `start_bit` 以内的所有字符，对区间内每个元素都相同，**完全不能用来缩小范围**，必须先跳过去。
2. **前缀可以当数值用。** 94 个字符正好可以用 94 进制编码成整数。任取 `k` 个字符，就得到值域 `[0, 94^k)` 上的一个整数，而**字典序与数值大小一致**——这是整个方案成立的基础。
3. **"某前缀对应数组的哪一段"可以预算。** 因为数组有序，所有前缀等于给定值的元素一定聚集在**连续一段**里。把每一段的起点记下来（前缀和），查询时就不用比较，直接查。

### 3.2 构建流程

对节点负责的区间 `[start, end]`：

1. **求公共前缀** `start_bit = lcp(row[start], row[end])`（以较短者长度为上限）。
2. **数值化**：`num0 = encode(row[start], start_bit, L)`、`num1 = encode(row[end], start_bit, L)`，其中 `L` 是截断长度。得到值域 `[num0, num1]`。
3. **定桶宽** `division`（见 §5）。
4. **建直方图与 CDF**：遍历区间内每个元素，算出它的桶号 `b = (v - num0) / division`，计数；再做前缀和，得到 `cdf[0..whole_size]`，满足
   `cdf[b] = 落在桶 0..b-1 的元素总数`。
5. **稠密桶递归**：若某桶元素数 `> λ × 阈值`，为它建子节点，子节点区间正是该桶对应的连续段，`index_node[b]` 记录"桶 b → 第几个子节点"（0 表示没有）。
6. **退化处理**：若公共前缀已经覆盖整个较短键（`start_bit ≥ min_len`），或截断长度超出字符串长度，则该区间无法再用数值细分，退化成**单桶**（整段交给二分）。

### 3.3 查询流程

```
① 公共前缀比对：key[0..start_bit) 与 row[node->start][0..start_bit) 逐字符比较
   不一致 → 该区间内不可能存在，返回 −1
② 数值化：v = encode(key, start_bit, end_bit - start_bit)
③ 桶号：k = (v - num0) / division，越界 → 返回 −1
④ 候选区间：low = cdf[k] + start, high = cdf[k+1] - 1 + start
⑤ 有子节点 → 递归到 children[index_node[k]-1]；否则在 [low, high] 内二分
```

**第 ③ 步不产生任何字符串比较**，这是 LI-Tree 与其它算法最本质的区别：其它算法都在"比较大小 → 猜位置"之间反复，而 LI-Tree 把"位置"直接算出来了。

### 3.4 一个具体例子

假设某节点负责 1,000,000 个元素，`start_bit = 0`，截断长度为 2 字符：

- 值域跨度最多 `94² = 8836`，取 `division = 1` 则 `whole_size = 8836`；
- 平均每个桶 `1000000 / 8836 ≈ 113` 个元素；
- 查询时算出桶号 → 在 113 个元素里二分，约 `log₂(113) ≈ 6.8` 次比较；
- 对比二分：`log₂(1000000) ≈ 19.9` 次。

这就是 §8 中"命中 6.15 次 vs 18.96 次"的来源。

## 4. 数据结构

```c
typedef struct LiNode {
    int start_bit;                /* 公共前缀长度 */
    int end_bit;                  /* 截断右端（开区间），编码区间 [start_bit, end_bit) */
    int start, end;               /* 负责的数组区间，闭区间 */
    long long start_num;          /* 截断前缀编码的区间下界（查询只需下界） */
    int whole_size;               /* 桶数 = cdf 长度 - 1 */
    int child_num;
    int division;                 /* 每桶覆盖多宽的值域 */
    int *cdf;                     /* whole_size + 1 个前缀和 */
    int *index_node;              /* whole_size 个：桶 b → 子节点编号（0 表示无） */
    struct LiNode *children;      /* child_num 个连续子节点 */
} LiNode;
```

```c
typedef struct {
    LiNode root;      /* 根节点内联，省一次分配 */
    LiTreeConfig cfg; /* scheme / cap / lambda */
    int count;
    int node_count;
    size_t memory;    /* 有效负载字节数 */
    size_t reserved;  /* 向系统申请的字节数 */
    void *arena;      /* 区域分配器（不对外暴露） */
} LiTree;
```

**两个刻意的设计选择**：

1. **区域分配器（arena）**：所有节点和数组都从 4 MiB 的块里按指针递增分配。构建时只有指针加法，没有上千次 `malloc`；释放时遍历块链表即可，不需要递归 `free`。
2. **子节点连续存放**：`children` 是 `child_num` 个**连续**的 `LiNode`，下标即编号。相比"指针数组 + 逐个 `malloc`"，省掉了一层指针跳转，也让子节点在内存中彼此相邻。

## 5. 两套构建方案

差别只在"桶有多宽"和"截断多长"这两个决策上。

### 5.1 方案一：定长 CDF（`--scheme 1`，默认）

**目标：让每个桶里平均装 `cap` 个元素，与数据规模无关。**

1. 从 2 字符起步。若当前仍是"每单位值挤了超过 `cap` 个元素"，就多加一个字符（值域扩大 94 倍），直到满足为止。
   判定条件：`(end - start + 1) / (num1 - num0 + 1) ≤ cap`。
2. 令 `per_value = (end-start+1) / span + 1`（平均每单位值挂多少元素），取
   `division = max(1, cap / per_value)`，
   `whole_size = (num1 - num0) / division + 1`。
3. 稠密阈值取 `thr = cap`，判定 `桶内元素数 > λ · cap`。

结果：`whole_size ≈ N / cap`，即桶数与 `N` 成正比、桶内元素数恒等于 `cap` 量级。

### 5.2 方案二：展开式稀疏 CDF（`--scheme 2`）

**目标：CDF 完全按值域展开，不做任何合并。**

1. 截断固定 2 字符（不加长）。
2. `division = 1`，`whole_size = 值域跨度`（最多 8836）。
3. 稠密阈值动态：`thr = max((end-start) / whole_size, 20)`，判定 `桶内元素数 > λ · thr`。

结果：`whole_size` 与 `N` 无关，**桶内元素数 = `N / 8836`，随 `N` 线性变差**。

### 5.3 为什么两者在 100 万条时完全相同

方案一在 100 万条时算出 `per_value = 114`，`division = max(1, 150/114) = 1`——正好退化成方案二。所以 §8.1 与 §8.2 的比较次数一字不差（6.1463）。

这正是原设计说明里"希望大致为 1 层"的含义：`cap=150` 下，100 万条数据刚好能被单个 2 字符截断的 CDF 覆盖。

### 5.4 什么时候必须用方案一

数据量涨到 500 万时，`N / 8836 ≈ 566` 个元素挤在一个桶里，方案二的桶内二分代价升到 8.42 次；而方案一自动把截断加长到 3 字符，`whole_size` 涨到 39552，桶内元素数回落到 126，比较次数保持在 6.31。

**结论：方案一的"自适应截断"是它相对方案二的核心价值，数据规模越大越明显。**

## 6. 数据集与分布

数据集是 5 种分布生成的字符串（对应原版 `data_generate.c` 的 5 个生成函数）：

| 名称 | 生成函数 | 形状 |
|---|---|---|
| `uniform` | `genrnd` | 每个字符在 94 个可打印字符中均匀取值 |
| `nd` | `genrndnd` | 首字符按正态分布（μ=47, σ=22）取尖峰，其余字符按正态（μ=47, σ=33） |
| `nd2` | `genrndnd2` | 首字符均匀；若首字符是 `'0'`/`'1'`，第二个字符以 94/110 的概率砸到固定值 |
| `normal` | `genrndnp` | 由单个正态数（μ=4418, σ=128）决定前两个字符 |
| `mix` | `genrndmg` | 混合高斯（μ=2209, σ=1628），一半概率平移到 4418 附近 |

共同约定：

- 长度：`rand() % (128 - 32) + 32`，即实际 31~126 字符；
- 只有前 1~2 个字符的分布被刻意塑形，其余字符均匀随机；
- 生成后按 `strcmp` 升序整表排序；
- 随机源是 **xorshift64\***，种子显式传入 —— 同种子必得同一份数据，实验可复现。

`li-gen --check` 会校验两件事：**是否真的有序**、**字符是否全部落在 `'!'`~`'~'`**。后者不是洁癖：如果数据里混入 `\0` 或控制字符，94 进制编码会算出非法值，索引就会算错。

```
src/
  common.h      常量、SearchResult、94 进制编码 li_encode、计数比较 li_cmp
  timer.h/.c    单调高精度计时（QPC / clock_gettime）+ 控制台 UTF-8 设置
  thread.h/.c   极简并行原语：核数探测 + 领取式任务池（Win32 / pthread，零依赖）
  dataset.h/.c  数据集：5 种分布生成、文本读写、有序性/字符范围校验、xorshift64*
  searcher.h/.c 四种基线算法（纯函数）+ 算法表 LI_ALGOS
  litree.h/.c   LI-Tree：区域分配器、构建、查询
  gen.c         li-gen   ← 原 data_generate.c
  demo.c        li-demo  ← 原 test_single.c / test_single_m2.c
  bench.c       li-bench ← 原 test_numbers.c / test_numbers_m2.c
```

**依赖方向**：`gen/demo/bench → {litree, searcher, dataset, timer} → common`，没有环。

`searcher.c` 里有一张统一的算法表：

```c
const LiAlgo LI_ALGOS[] = {
    {"binary",            ad_binary,            0},
    {"interpolation",     ad_interpolation,     0},
    {"interpolation-low", ad_interpolation_low, 0},
    {"cut",               ad_cut,               0},
    {"li-tree",           li_litree_search_fn,  1},  /* 1 = 需要索引上下文 */
};
```

所有算法签名统一为 `SearchResult fn(void *ctx, char *const *row, int n, const char *key)`，因此基准程序用**同一个循环**跑遍全部算法，不存在"某个算法被特殊对待"导致的不公平。

## 8. 实测结果

> 全部数字可用 `make run-bench` / `make run-bench-5m` 在本机复现。
> 环境：gcc 8.1.0 (MinGW-w64)、`-O2`、Windows x64、桌面级 CPU。
> **比较次数是确定性的**（同种子同数据必然相同）；**耗时会有 ±20% 的波动**，看量级即可。

### 8.1 100 万条 · 方案一 · cap=150

`li-gen --count 1000000 --dist nd --seed 1`，10 万次查询/组，建索引重复 3 次取平均。

| 算法 | 命中·比较 | 命中·耗时 | 相对二分 | 未命中·比较 | 未命中·耗时 |
|---|---|---|---|---|---|
| 二分 | 18.9556 | 0.526 µs | 1.00× | 19.9513 | 0.447 µs |
| 插值 | 5.1836 | 1.355 µs | 2.58× | 5.5972 | 1.008 µs |
| 简易插值 | 68879.2 | 382.7 µs | 728× | 69005.8 | 349.7 µs |
| 割线 | 4.9532 | 1.202 µs | 2.29× | 5.1499 | 1.096 µs |
| **LI-Tree** | **6.1463** | **0.351 µs** | **0.67×** | **6.6798** | **0.347 µs** |

索引：**1 个节点**，8836 个桶，截断 `[0,2)`，有效负载 69.0 KiB（0.1 字节/键），建索引 ≈ 10 ms。

> 只建出 1 个节点是因为没有哪个桶超过稠密阈值 `3 × 150 = 450` 个元素（平均 113 个）。数据结构本身支持多层递归，阈值由 `λ` 控制。

### 8.2 100 万条 · 方案二

| 指标 | 方案一 | 方案二 |
|---|---|---|
| 建索引 | 9.77 ms | 8.09 ms |
| 节点 / 桶数 / 截断 | 1 / 8836 / [0,2) | 1 / 8836 / [0,2) |
| 命中·比较 | 6.1463 | 6.1463 |
| 命中·耗时 | 0.351 µs | 0.367 µs |
| 未命中·比较 | 6.6798 | 6.6798 |

**两方案完全重合**，原因见 §5.3。

### 8.3 500 万条 · 两方案对比（关键结论）

`li-gen --count 5000000 --dist nd --seed 1`，2 万次查询/组（简易插值在这个规模下要做 34 万次比较，故减少查询量）。

| 方案 | 建索引 | 节点 | 桶数 | 截断 | 桶内平均元素 | 命中·比较 | 命中·耗时 | 相对二分 |
|---|---|---|---|---|---|---|---|---|
| 一（定长 CDF） | 42.8 ms | 1 | **39552** | **[0,3)** | 126 | **6.3075** | 0.598 µs | **0.77×** |
| 二（展开式稀疏） | 39.1 ms | 1 | 8836 | [0,2) | 566 | 8.4168 | 0.752 µs | 0.95× |

同规模下的其它算法（命中）：二分 21.3274 / 0.779 µs，插值 6.4495 / 2.225 µs，简易插值 344115.9 / 2022.5 µs，割线 4.8556 / 1.826 µs。

**结论**：方案二的 CDF 长度被 94² 钉死，元素一多桶就撑爆；方案一靠"多截一个字符"把桶数扩了 4.5 倍，比较次数基本不涨。**这是全项目最重要的一个实验发现。**

### 8.4 调参：cap 的影响（100 万条 · 方案一 · 5 万次查询）

| cap | 桶数 | 命中·比较 | 命中·耗时 |
|---|---|---|---|
| 30 | 55373 | 3.7751 | 0.350 µs |
| 50 | 33224 | 4.3982 | 0.370 µs |
| 100 | 16612 | 5.2973 | 0.377 µs |
| 150（默认） | 8836 | 6.1463 | 0.351 µs |
| 300 | 4418 | 7.1083 | 0.347 µs |

**比较次数几乎减半（7.11 → 3.78），但耗时纹丝不动（≈0.35 µs）。** 见 §8.5。

### 8.5 为什么"比较次数少"不等于"更快"

把 §8.1 与 §8.4 放在一起看，会出现两个反直觉现象：

1. **插值/割线的比较次数只有二分的 1/4，墙钟时间却是二分的 2.3~2.6 倍。**
2. **cap 从 300 降到 30，比较次数砍半，耗时不变。**

原因有三：

- **每次"比较"的成本天差地别。** 二分与 LI-Tree 的比较是纯 `strcmp`，字符串在前几个字节就分出大小，而且访问的是连续下标的行（大概率命中缓存）。插值/割线每一步都要做一次 94 进制编码（几十条整数乘加）、一次除法、一次跨缓存行的访存，成本相当于几十次 `strcmp` 的比较动作。
- **访存是真正的瓶颈。** 每行 128 字节，一次 `strcmp` 基本就要碰一条新的缓存行。在 100 万条（128 MB 数据）规模上，索引命中率本来就低，减少比较次数换不来时间。
- **CDF 定位不是免费的。** 它虽然不做字符串比较，但也要编码 + 除法 + 一次随机访存；cap 越小、CDF 越长，查表本身的缓存缺失反而增加，正好抵消了比较次数下降的收益。

**工程含义**：想在这个负载上再提速，应当改**数据布局**（变长紧凑存储、把前缀也放进索引以减少 `strcmp` 的字节数），而不是继续压比较次数。


### 8.7 多核扩展性

`--threads N` 同时作用于两个热点：**查询循环**和**建索引时的节点直方图**。`--threads 0` 表示用满全部核，默认 1（保持与 §8.1~§8.4 的单线程数字可比）。

**查询循环的扩展性**（100 万条 · 方案一 · 10 万次查询 · 命中组）：

| 线程 | 二分 | 加速比 | LI-Tree | 加速比 | 插值 | 加速比 |
|---|---|---|---|---|---|---|
| 1 | 0.4684 µs | 1.00× | 0.3717 µs | 1.00× | 1.1689 µs | 1.00× |
| 2 | 0.2299 µs | 2.04× | 0.1649 µs | 2.25× | 0.4752 µs | 2.46× |
| 4 | 0.1138 µs | 4.12× | 0.0818 µs | 4.54× | 0.2019 µs | 5.79× |
| 8 | 0.0708 µs | 6.62× | 0.0510 µs | 7.29× | 0.1134 µs | 10.31× |
| 16 | 0.0528 µs | 8.87× | 0.0378 µs | 9.83× | 0.1065 µs | 10.98× |

16 线程时吞吐约 **1895 万次/秒**（命中组）、**2272 万次/秒**（未命中组）。

**建索引的扩展性**：

| 线程 | 100 万条 | 加速比 | 500 万条 | 加速比 |
|---|---|---|---|---|
| 1 | 7.85 ms | 1.00× | 41.3 ms | 1.00× |
| 2 | 5.25 ms | 1.49× | — | — |
| 4 | 4.37 ms | 1.80× | 22.4 ms | 1.84× |
| 8 | 3.72 ms | 2.11× | 17.0 ms | 2.43× |
| 16 | 3.27 ms | 2.40× | 15.4 ms | 2.69× |

**三点结论**

1. **查询循环能接近线性，建索引不能。** 建索引的直方图必须扫过全部行（500 万条 ≈ 320 MB 有效流量），16 线程时已经撞上内存带宽上限，加速比停在 2.7×；查询循环的计算占比更高，LI-Tree 能到 9.83×。
2. **超线程的收益有限。** 本机 32 个逻辑核，16 线程时 LI-Tree 拿到 9.83×、二分 8.87×（约为线程数的 61% / 55%），符合"延迟/带宽受限 + SMT"的典型表现。
3. **不同算法的扩展性不同**：插值法在 16 线程上加速 10.98×，高于二分的 8.87%。原因是插值法每步都要做 94 进制编码与除法，**计算密集**、对内存带宽不敏感；二分则是纯粹的访存延迟打点。这也让多线程下"插值 vs 二分"的相对差距从 2.50× 收窄到 2.02×。
4. **线程数不是越多越好，取决于查询总量。** 线程创建开销是固定的一份（每个约几十微秒），查询太少时它会盖过并行收益：同样 32 线程，2 万次查询时吞吐只有 981 万次/秒（每线程仅 625 次查询，创建线程的时间都快赶上计算时间），10 万次查询时则是 2580 万次/秒（LI-Tree 单次 0.0308 µs，比 16 线程的 0.0378 µs 还快）。**经验值：查询数应不少于 `线程数 × 1000`。**

**实现要点**

- **查询并行**：把 `--queries` 切给 `tasks = min(threads, queries)` 个任务，任务用原子计数器领取（动态负载均衡，因为单次查询快慢不一）。每个任务写自己的比较次数/错答小计，最后汇总。
- **随机流**：task 0 沿用全局种子，其余任务用 `seed ^ (黄金分割常数 × task)`，RNG 状态用线程局部存储。这样 **`--threads 1` 与单线程版本逐位一致**（已实测：18.9556 / 5.1836 / 4.9532 / 6.1463 等与 §8.1 完全相同）；多线程时各任务随机流独立，平均比较次数波动约 ±0.2%（18.9556 → 18.9506）。
- **建索引并行**：只并行"直方图"这一步——把节点区间切成 `chunks` 段，每个线程只往自己的局部桶数组累加（互不共享可写内存，**不需要锁**），最后串行合并。局部直方图总量受 32 MiB 上限约束，超出则减少分块数。
- **递归保持串行**：节点创建仍在单线程里完成，因此区域分配器完全不需要加锁，正确性风险最低。
- **并行不改变索引内容**：实测 1 线程与 16 线程构建出的索引，`li-demo` 的三组查询结果（位置 + 比较次数）**逐行完全相同**。
- **为什么不用 OpenMP**：MinGW 的 `-fopenmp` 会引入 `libgomp` 运行时 DLL，分发 exe 容易缺文件。`thread.c` 直接用 Win32 `CreateThread` / POSIX `pthread`，任务领取用 GCC 的 `__atomic_fetch_add`（无需额外库），编译即用、零第三方依赖。

## 9. 与原版实现的差异

原版是 2022 年的实验代码，四个互相复制粘贴的单文件。重构后算法思路不变，但修掉了 9 处缺陷、重做了工程结构。

### 9.1 工程化

| 项 | 原版 | 现在 |
|---|---|---|
| 代码组织 | 6 个 `.c`，同一套算法各复制一份（改一处要改四遍） | 5 个模块 + 3 个薄主程序，零重复 |
| 数据集存储 | `char str[num][len]` **开在 `main` 的栈上**（500 万条 ≈ 640 MB） | 堆上连续块 + 行指针数组 |
| 排序 | `qsort` 直接搬 128 字节的记录 | 只交换行指针 |
| 索引内存 | 每节点、每数组各自 `malloc`，一次构建上千次调用；构建时先 `malloc` 再覆盖（泄漏） | 区域分配器，构建只有指针加法，释放一次遍历 |
| 子节点 | `Index **Nodes` 二重指针 | `child_num` 个连续节点 |
| 冗余字段 | `start_positions` / `end_positions`（原设计说明自己标注"冗余"） | 已删除 |
| 直方图 | `int pdfs[whole_size]` 变长数组（方案二下可能上千项，撑爆栈） | 直接在 `cdf[b+1]` 计数再原地前缀和，零额外数组 |
| 参数 | `cap`、文件名、数据条数全是编译期常量/字面量 | 全部命令行参数 |
| 随机性 | `ftime()` + `rand()` 播种，两次运行数据不同 | 显式种子 xorshift64*，可复现 |
| 计时 | 每查一次调两次 `clock()` 再累加 | 整段循环计时 / 次数（QPC，亚微秒） |
| 正确性校验 | 只统计比较次数，查错了看不出来 | 每次校验"返回位置上的字符串 == key"，统计错答 |
| 输出 | `printf` 写在查找函数的循环里 | 查找函数是纯函数，输出全交给主程序 |
| 跨平台 | `struct timeb` / `ftime`（Windows 专有） | Windows 用 QPC，其它平台用 `clock_gettime` |
| 编码 | GBK；两个 `_m2.c` 的注释还是二次编码损坏 | 全 UTF-8 |

### 9.2 缺陷修复（9 条）

**① 每个节点漏掉区间最右端的键**（最严重）

原版统计直方图写的是 `for (i = start; i < end; ++i)`，但区间语义是**闭区间** `[start, end]`：根节点传 `0, num-1`，子节点传 `cdfs[i+1]-1+start`。于是每个节点负责区间的**最后一个元素永远进不了索引**。

*实测证据*：把原版 `test_single.c` 加上探针编译（并调大栈），跑 10 万条数据：

```
最大键 下标 99999 : 二分 命中, ACDF 未命中(漏键)
随机 1000 个存在的键: 二分命中 1000 个, ACDF 漏掉 0 个 (0.0%)
```

只有每个节点的边界键受影响，命中概率约 `节点数 / N`，所以平时发现不了；而 `test_numbers.c` 版本返回的是"比较次数"而不是位置，漏判时照样返回一个正常数字，基准结果里完全看不出来。

现在循环改为 `i <= end`，`li-demo` 的「边界」用例专门回归这一点。

**② 退化分支字段未初始化**

公共前缀已覆盖较短键时，原版只设了 `cdf/child_num/index_node` 就 `return`：`start_num`、`division` 是未初始化的垃圾值（根节点在栈上，子节点是 `malloc` 出来的），查询侧据此算出的桶号是随机数。现在显式置 `start_num=0, division=1, end_bit=start_bit`，语义为"整段一个桶，直接二分"。

**③ `test_file.c` 把数据文件覆盖成一行**

写完 500 万行后用 `"w+"` 重开同一个文件只写一句时间。生成与计时现在彻底分开。

**④ 插值法上界写成 `mid + 1`**

`Interpolation_Search` 在 `key < str[mid]` 时把上界设成 `mid + 1`：既没排除 `mid`，当 `mid == high` 时还会读到 `row[n]` 越界。改为 `mid`。

**⑤ 跳跃步长 `j` 从不重置**

`i += pow(3, j)` 里的 `j` 声明在循环外、只增不减，于是外层每多迭代一次，跳跃步长就膨胀 3 倍，最后基本等于"整段二分"，把插值法的优势整个抵消掉。现在每次跳跃都从 1 重新开始，用整数递推替代浮点 `pow`，并防止下标溢出。

**⑥ 插值/割线落点没有夹逼**

算出的 `mid`、`new_x` 完全可能落在 `[0, n-1]` 之外，原版直接拿去 `str[mid]`。现在所有落点都夹到闭区间内，越界即退回二分。

**⑦ `strcmp` 返回值被假设成 ±1**

原版到处写 `strcmp(...) == -1`。标准只保证返回正/零/负。现在统一用 `< 0` / `> 0`。

**⑧ `division` 可能为 0**

`*_m2.c` 里除 `generate_index_m2` 外还留着一份旧的 `generate_index`，其 `division = part / cap`（`part` 是"每单位值的元素数 + 1"，通常远小于 `cap`），绝大多数数据下算出 **0**，接着就是 `number / division` 除零。这份变体 `main` 没调用，但留在文件里没删。重构版只保留两种有意义的方案，并对 `division` 做 `>= 1` 兜底。

**⑨ 编码混乱**

6 个 `.c` 全是 GBK；两个 `_m2.c` 的中文注释还是二次编码损坏（UTF-8 被当 GBK 存过一遍），已不可读。重构版全部 UTF-8。

### 9.3 保真度验证

原版交付的 `test_numbers.exe` / `test_numbers_m2.exe` 可以直接运行，因此可以在**同一份数据**上做严格对照（比较次数是确定性指标）。

**100 万条（原 `Datatest4.txt`）**，原版 100 万次查询 vs 重构版 10 万次查询：

| 算法 | 原版平均比较 | 重构版平均比较 | 偏差 |
|---|---|---|---|
| 二分 | 18.952090 | 18.9556 | < 0.02% |
| 割线 | 9.795635 | 5.0438 | −48% |
| 插值 | 18.285855 | 5.5097 | −70% |
| **ACDF（LI-Tree）** | **6.385564** | **6.3908** | **< 0.1%** |

**500 万条（原 `Datatest1.txt`，方案二）**，原版 200 万次查询 vs 重构版 10 万次查询：

| 算法 | 原版平均比较 | 重构版平均比较 | 偏差 |
|---|---|---|---|
| 二分 | 21.320825 | 21.3215 | < 0.01% |
| 割线 | 8.435147 | 4.3675 | −48% |
| 插值 | 10.332382 | 6.0762 | −41% |
| **ACDF（LI-Tree）** | **8.196986** | **8.2010** | **< 0.05%** |

**怎么读这张表**：

- **二分与 LI-Tree 的偏差都在 0.1% 以内**，说明重构没有改变算法行为，两套方案的实现与原版等价；这点差异来自缺陷 ①（漏掉边界键）的修正和随机查询序列的细微不同。
- 插值和割线的比较次数**明显下降**，是刻意修掉缺陷 ④⑤⑥ 的结果——这两项缺陷让跳跃步长指数膨胀、最后退化成整段二分，把插值法的优势吃掉了。**所以这两行的差值不是"实现不同"，而是"原版有 bug"。**
- 所有查询都做了"返回位置上的字符串是否真的等于 key"的校验，**错答次数全为 0**。

> 关于原版的"耗时"列：它每查一次调两次 `clock()` 再累加。`clock()` 的粒度远大于单次查找本身，累加结果实际反映的是"查询过程中跨过的时钟滴答数"，不能当真实耗时用；而且不同文件里的归一化因子还不一致（`rate = tf/Re`，一个文件是 1、另一个是 0.5）。本文档一律改为"整段循环墙钟时间 / 次数"。
>
> 上述对照组使用的 `Datatest4.txt` / `Datatest1.txt` 与原始源码已在仓库清理时移除（原数据由时间种子生成，无法逐字节复原）。这两张表仅作为**保真度证据**保留；§8 的表格才是可从仓库复现的正式结果。

### 9.4 有意保持一致的部分

## 10. 复杂度分析

设 `N` 为元素数，`L` 为截断字符数（2~3），`B` 为总桶数，`D` 为深度。

| 操作 | 复杂度 | 说明 |
|---|---|---|
| 求公共前缀 | `O(min_len)` | 只在区间首尾两个元素间比较 |
| 单节点直方图 | `O(节点元素数 × L)` | 每元素做一次 `L` 位编码 |
| 单节点前缀和 | `O(whole_size)` | |
| 整树构建 | `O(N·L·D + B)` | 实际测得 100 万条 ≈ 10 ms，500 万条 ≈ 43 ms |
| 查询 | `O(start_bit + L + log₂(桶内元素数))` | `start_bit` 是字符比较，与位置无关 |
| 查询（最坏） | `O(start_bit + L + log₂ cap)` | 桶内退化成二分时的上界 |
| 索引空间 | `O(B + 节点数)` | 实测 69 KiB / 100 万元素 ≈ 0.07 字节/键 |
| 数据空间 | `O(N × 128)` | 定长槽位，100 万条 = 128 MB |

**关于 `N` 的敏感性**：

- 方案一：桶内元素数恒为 `cap`，查询成本**与 `N` 无关**（`N` 增大时靠加长截断维持）；
- 方案二：桶内元素数 = `N / 8836`，查询成本**随 `N` 对数增长**。

这就是 §8.3 中两者在 500 万条上出现差距的数学原因。

## 11. 原设计说明归档

原仓库附有一份 6 页的设计说明 PPT（`说明.pptx`），已在仓库清理时移除。其要点整理如下，作为设计意图的原始记录。

**第 1 页 · 文件说明**

- `test_single.c`：一次实验，包含全部搜索方法和 `main`；
- `test_numbers.c`：多次实验，与上面文件的区别在于各搜索法返回的是**搜索次数**而不是位置；
- `data_generate.c`：模拟文件生成，含多种分布；
- 使用顺序：先用 `data_generate` 生成模拟数据 txt，再运行 `test_single` 或 `test_numbers` 得到结果。

**第 2 页 · 生成文件**

`void generater()` 是生成函数，5 种分布：`genrnd` 均匀、`genrndnd` 特殊位置尖峰、`genrndnd2` 两个尖峰、`genrndnp` 正态、`genrndmg` 混合高斯双峰。

**第 3 页 · 函数说明**

查找方法从上到下是二分法、插值法、简易插值法和割线搜索法。输入为 `str[num][len]`（`len` 固定，默认 128）与 `key`。返回位置 `position`，不存在返回 −1；统计搜索次数的文件里返回的是搜索次数 `count`。高阶搜索法都有截断位数问题，目前设置起始位置 `tran = 0`、`inc` 为截断个数；也有"搜索范围小于多少之后转为二分搜索"的阈值。`search_result` 负责打印 `position`。

**第 4 页 · LI-Tree 的说明**

总结构从上到下是：字符串的数目、字符串的长度、字符串组（**并未使用**）、LI-Tree 的根结点。实际实验中并没有使用结构里的 `char **` 二重指针（是空的）。

**第 5 页 · LI-Tree 数据结构实现**

节点数据结构 `Index *` 记录：结点的截断区间、起始位置、末尾位置；节点通过进制法转化得到的起始数字与末尾数字；`cdf` 大小为 `whole_size + 1`；各子节点的起始位置和末尾位置（**冗余信息**，但如果涉及 CDF 的稀疏压缩就可能不是了）；除数 `division`——**这里使用的是方案一，希望大致为 1 层**；子节点个数 `child_num`；子节点编号 `int index_node[whole_size]`，记录每一片 CDF 对应的子节点编号和有无，数值为 0 表示无结点、记录为 `i` 则结点位置是 `Nodes[i-1]`；子节点设为二重指针，实际是 `Index * Nodes[child_num]`；`level` 是冗余信息，也非必须。

**第 6 页 · LI-Tree 相关函数算法**

- 生成函数输入：`str[num][len]`、`start` 起始位置、`end` 末尾位置、`Node` 指针、`level` 层数（冗余）；用法 `generate_index(num, str, 0, num-1, Node, 0)`。
- 搜索函数输入 `key`；用法 `index_search(num, str, 0, Node, key, 0)`，存在返回位置，不存在返回 −1。
- 另有内存释放函数。

> 对照 §9.2 可以看到：这份设计说明里明确指出"`start_positions` / `end_positions` 是冗余信息"、"`level` 非必须"、"`char **` 并未使用"，重构版据此删除了这三个冗余项；说明里"希望大致为 1 层"的设计目标，也正好被 §5.3 的实测数据印证（100 万条时 `division` 确实收敛到 1）。

## 12. 已知限制与后续计划

**限制**

- **字符集固定**：只支持 94 个可打印 ASCII、槽宽固定 128 字节。含中文、含 `\0`、超过 127 字符的数据需要先改造编码与槽宽。
- **静态索引**：只支持构建后查询，没有插入/删除。
- **计数不等于时间**：CDF 定位本身是 O(1)，但常数不小（一次 94 进制编码 + 一次除法 + 一次随机访存），所以比较次数少 3 倍时墙钟只快 10~25%。
- **`interpolation-low` 是 O(n)**：作为"朴素对照基线"保留。在数据局部聚集时会退化到几十万次比较，这是它应有的表现，不是缺陷。
- **CDF 用 `int32`**：元素数超过 2³¹ 会溢出（当前上限 500 万，余量充足）。
- **CDF 未压缩**：原设计说明提到的"稀疏压缩"没有实现；方案二在大 `N` 下正是因为 CDF 覆盖不了全部值域才需要靠子节点补偿。
- **并行的覆盖面有限**：只并行了查询循环与节点直方图。递归建树、区域分配器仍是串行的（因此不需要锁），`li-gen` 的排序（`qsort`）也没有并行化——500 万条数据的生成+排序要 29 秒，主要花在这里。

**后续可以做的事**

1. **变长紧凑存储**：把定长 128 字节改成偏移表 + 紧凑字符块，减少缓存缺失——按 §8.5 的分析，这是最有可能真正提速的方向。
2. **CDF 位压缩**：`whole_size` 很大时用差分/位宽压缩，减少查表时的缓存缺失。
3. **前缀下推**：把 `start_bit` 处的字符也纳入索引，减少 `strcmp` 需要比较的字节数。
4. **自适应 `cap`**：按 `N` 与实测桶内分布自动选 `cap`，而不是固定 150。
5. **更细的并行粒度**：把递归子树也并行化（需要给区域分配器加锁或改成按子树独立分配），并给 `li-gen` 的排序换成并行排序——目前 500 万条数据要 29 秒，是复现实验时最大的等待。
6. **更多数据形态**：加入有大量重复键、公共前缀极长（如 URL、文件路径）的真实数据集。

## 13. 附录：术语表

| 术语 | 含义 |
|---|---|
| **公共前缀 `start_bit`** | 区间首尾元素的共同前缀长度；这段字符对区间内所有键都相同，不参与索引 |
| **截断 `[start_bit, end_bit)`** | 参与 94 进制编码的字符区间，长度 2~3 |
| **值域 `[num0, num1]`** | 截断前缀编码后的整数范围 |
| **桶 `bucket`** | 值域按 `division` 切分后的一个等宽小区间 |
| **`whole_size`** | 桶数，等于 `cdf` 长度减 1 |
| **CDF** | 前缀和数组，`cdf[b]` = 桶 b 之前的元素总数 |
| **`division`** | 每个桶覆盖多宽的值域（=1 表示不合并） |
| **稠密桶 / `λ`** | 元素数超过 `λ × 阈值` 的桶，需要建子节点继续细分 |
| **`cap`** | 方案一的桶内目标元素数，默认 150 |
| **方案一 / 方案二** | 定长 CDF（自适应截断）/ 展开式稀疏 CDF（固定 2 字符截断） |
| **ACDF** | 原版对这套索引的称呼，即本项目所说的 LI-Tree |
